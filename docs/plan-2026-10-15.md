## 四、根因：现有任务集不可能产生 Context 信号

六个任务的基线各为 185–281 字节的单文件，预算为 6–8 步、6,000 Token、60 秒墙钟。在这一规模下：

- `full_history` 的输入始终远小于预算，没有压缩需求；
- 六种策略构建出的 View 事实上收敛到同一组消息；
- 脚本模型动作固定，不随 Context 改变决策。

因此 `benchmarks/plan.json` 只能验证评测链路，**消融实验必须使用更大规模、真实模型才可完成的任务**。

## 五、后续计划

### P0 收口（零成本）

1. 推送仓库，让 CI 在 GitHub 托管环境首次真实运行。
2. 对外材料统一使用 `docs/resume-material.md` 的措辞，删除第三节全部数字。

验收：CI 在托管环境通过；对外文案与 `docs/` 证据一一对应。

### P1 真实消融（当前主线）

1. **DeepSeek 适配器有界重试与退避** —— 已完成：对 408/429/5xx 与传输错误做默认 3 次尝试、指数退避、受本步剩余超时约束；尝试次数写入 `model_response` / `model_error`；4xx 与确定性解析错误不重试。失败的尝试没有 Usage，本地统计与供应商账单的差异已写入 `docs/evaluation.md`。
2. **建立具备 Context 压力的真实任务集** —— 已完成：`benchmarks/real/` 下六个任务（duration、inventory、pipeline、textrefactor、config_migration、logtriage），每个任务含 README 契约、初始失败的公开测试、封面文档规则的留出测试与参考修复；`tests/test_real_tasks.py` 在 CI 中断言基线必红、参考修复后公开与留出测试必绿。六个任务已通过 Docker 确定性批次 36/36，Trace 与输入快照校验通过。
3. **提高重复次数** —— 计划已就绪：`benchmarks/real-context-plan.json` 为 6 任务 × 6 策略 × 5 次，共 180 次；`benchmarks/pilot-plan.json` 为 12 次小批次。价格快照守卫上限分别为 $43.36 与 $2.65。
4. **产出结论** —— 待真实批次执行：按策略报告 Token、费用、缓存命中率、成功率及配对差值；无论结论正负都如实记录并更新 `docs/experiment-report.md`。

验收：一份可校验的真实模型实验（每任务每策略 ≥5 次），`experiment-verify` 与锚点通过；未知 Usage 不再使策略均值整体为 `null`。

### P2 Trace 差分案例化

对失败运行与同任务同策略的成功运行做 `trace-diff --report`，把首个分叉归类为模型决策 / 工具执行 / Context 构造，写入 `docs/`，并给 `summary.json` 增加分叉类别统计。

验收：≥2 篇可核验案例；分类统计出现在实验汇总中。

### P3 工程硬化

`PluginGroup` 接入 CLI 动态加载 · 中断的 `eval` 支持 resume · 工作区快照升级并补故障注入测试 · 阻塞中模型请求的取消语义 · 宿主机 Shell 默认容器化。

### P4 离线规模（可选）

若要保留"千次离线执行"表述，应改为**故障覆盖**口径：6 任务 × 6 策略 × 注入（超时、预算耗尽、MCP 失败、中断恢复、畸形模型输出）× 多轮，得到 1,000 次以上可校验运行。重复同一套固定动作不做数。

## 六、非目标

- 不把脚本模型实验当作策略能力证据。
- 不在缺少输入快照与缓存拆分的旧 Trace 上补算费用结论。
- 不在供应商不稳定期间发起批量付费调用；真实批次的预算阈值需在运行前确认。
